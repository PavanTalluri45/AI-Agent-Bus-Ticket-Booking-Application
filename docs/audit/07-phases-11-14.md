### Plain-English Concept Explanations
- **Advisory Locking (`pg_advisory_xact_lock`)**: In `hold_service.py:326`, PostgreSQL transaction-level advisory locks prevent double-booking race conditions when two users click "Hold" on the same seat at the exact same millisecond. The lock hashes the composite key `(schedule_id, seat_id)`.
- **Row-Level Locking (`FOR UPDATE`)**: Used during booking creation (`booking_service.py:96`), payment verification (`payment_service.py:171`), and finalization (`booking_finalization_models.py:78`). Prevents race conditions where a hold could be converted twice or paid twice simultaneously.
- **Hold Expiry Lifecycle**: Holds automatically expire in 10 minutes (`expires_at = NOW() + 10m`). If a user attempts to create a booking on an expired hold, `booking_service.py:35` raises `HoldExpiredError`, and the seat is made available to other passengers.
- **Idempotent Retries**: If a network glitch causes the frontend to retry an approval request or payment verification, the backend checks whether the operation already succeeded and returns the existing resource instead of creating duplicate records or throwing errors (`test_integrated_agent.py:3728-3777`).

# Phase 12: Cost + Performance Optimization

### Objective
Optimize model token usage, reduce round-trips, mitigate process/connection startup latency, implement connection pooling, caching, rate limiting, and performance profiling.

### Current Implementation Assessment
> [!NOTE]
> **Implemented Optimizations:**
> 1. LangGraph PostgreSQL Connection Pooling (`psycopg_pool.ConnectionPool` min=1, max=5 at `test_integrated_agent.py:3551`).
> 2. Context Window Stripping: Large UI-only data (`seat_map` ~40 seats) stripped from LLM prompt (`test_integrated_agent.py:899`).
> 3. Server-Sent Events with thread-local streaming.
> 4. User-level token and rate limiting (`check_rate_limit()` 20 req/min).
> 
> **Proposed / Unimplemented Optimizations:**
> 1. MCP Subprocess Startup Overhead: Currently, `call_mcp_tool()` launches a new Python process (`sys.executable mcp_server.py`) for **every** tool call (`test_integrated_agent.py:817-823`), adding ~300-600ms latency per tool execution. A persistent background server or in-process fast-path would eliminate this.
> 2. API Key Failover: Only a single `GEMINI_API_KEY` is loaded. No multi-key rotation on quota exhaustion.
> 3. Model Token Cost Monitoring: Tokens printed to stdout, but not aggregated into billing metrics or Redis counters.

# Phase 13: LangChain + LangGraph

### Objective

### Architectural Reality: LangChain vs LangGraph
> [!IMPORTANT]
> - **LangGraph is the core orchestration framework** of the application. It manages all graph execution, state transitions, PostgreSQL checkpointer persistence, thread isolation, and human-in-the-loop interrupts.
> - **LangChain is NOT directly used for prompt templates in production code.** The project uses plain Python string formatting and typed JSON structures in `build_llm_input()` (`test_integrated_agent.py:887`). Only `langchain_core.runnables.RunnableConfig` is imported (as required by LangGraph).
