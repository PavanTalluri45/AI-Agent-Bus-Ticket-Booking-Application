# Phase 08: Multi-Agent Architecture

### Objective
Explore patterns for multi-agent systems (supervisors, hierarchical delegation, agent handoffs, shared state, inter-agent communication, and failure isolation); contrast with single specialized agent systems.

### Architectural Reality in this Repository
> [!IMPORTANT]
> The repository **intentionally implements a single specialized bus-booking agent** (`StateGraph` in `test_integrated_agent.py:3361-3578`). No multi-agent hierarchy or supervisor-worker topology is implemented or running in production.

### Files
- `src/bus_booking_ai_agent/phase_04_langgraph/test_integrated_agent.py` (Single-agent implementation)
- `.agents/skills/supabase-postgres-best-practices/SKILL.md` (Workspace customization rules)

### Test Files
- None for multi-agent (no multi-agent system exists).

### Plain-English Concept Explanations
- **Single vs Multi-Agent**: A single-agent architecture handles all tasks within a unified state graph. For bus booking, this single agent is optimal because search, stop selection, seat layout, seat hold, and booking creation are sequential stages of one linear transactional workflow. Splitting this into multiple agents (e.g. "search agent", "seat agent", "payment agent") would introduce handoff serialization latency, distributed state synchronization overhead, and redundant model round-trips without practical benefit.
- **Why Multi-Agent is Not Implemented**: The repository maintains a deliberate design decision to keep the orchestrator simple, deterministic, and highly auditable. Concepts like supervisor routing and hierarchical agents were studied conceptually during architectural planning, but not built into code.

# Phase 09: Observability

### Objective
Track, trace, and monitor agent execution in real-time: node transitions, tool calls, model latency, token consumption, correlation IDs, error boundaries, structured logging, and frontend execution visibility.

### Current Implementation Assessment
> [!NOTE]
> The application has **exceptional real-time user-facing visibility** via Server-Sent Events (`step_events.py` streaming live step states to the frontend `AgentSteps` UI component). However, backend production telemetry relies largely on terminal `print()` statements and lacks OpenTelemetry, LangSmith tracing, or an aggregated metrics dashboard.

### Files
- `src/bus_booking_ai_agent/phase_04_langgraph/step_events.py` (Live step event emitter)
- `main.py:1061-1126` (`_stream_agent_turn` SSE generator)
- `frontend/components/chat/agent-steps.tsx` (Frontend step viewer)
- `frontend/components/chat/bus-booking-chat.tsx:49-57, 81` (Live step aggregation)
- `src/bus_booking_ai_agent/phase_04_langgraph/test_integrated_agent.py` (Console print instrumentation)

### Test Files
- `tests/test_chat_components.py` (Verifies UI component rendering of steps)

### Plain-English Concept Explanations
- **Live Step Events (`step_events.py`)**: A ContextVar-based event emitter allowing deep graph nodes (`llm_node`, `tool_node`, `hold_execution_node`) to emit real-time status events (`begin_step("Searching buses")`, `emit_done("Found 3 buses")`) without polluting graph state.
- **Server-Sent Events (SSE)**: The endpoint `/api/v1/chat` keeps a persistent HTTP connection open, yielding `event: step` as nodes run and `event: final` when the turn finishes.
- **Latency & Token Measurement**: Console banners print microsecond-precision timings using `time.perf_counter()` for Gemini API requests (`t_elapsed`), tool executions (`t_mcp_elapsed`), and PostgreSQL checkpointer reads (`checkpoint_time`).
- **What is Missing**: Correlation IDs / Request IDs (`X-Request-ID`) are not passed in headers. No centralized log aggregator (e.g. Datadog, Grafana Loki). No LangSmith integration (`LANGCHAIN_TRACING_V2=true` is not configured).

# Phase 10: Evaluation

### Objective
Systematically test, evaluate, and benchmark agent behavior: unit tests, integration tests, golden test cases, tool selection accuracy, hallucination prevention, regression suites, and failure analysis.

### Current Implementation Assessment

### Plain-English Concept Explanations
- **Ordinary Tests vs AI Evaluation**: Ordinary software tests check deterministic code (assert function returns expected dictionary). AI evaluation benchmarks the non-deterministic LLM across 100+ sample queries measuring semantic correctness, hallucination rate, and tool call precision.
- **Golden Test Cases in Repo**: `tests/test_seat_hold_workflow.py` contains extensive golden test cases for natural-language stop phrasing ("Board from Bangalore and drop at Chennai", "Bangalore to Chennai", "Pickup Ameerpet", nested stop subsumption).
- **Hallucination Prevention**: Enforced deterministically in code via `resolve_booking_context()` and `validate_arguments_against_booking_context()`. If Gemini hallucinates a schedule UUID or seat ID, the backend rejects it with `ToolGuardrailError`.
